## 1. 한 문장 요약

> 터미널에서 쓰는 가계부 프로그램을 Python으로 만들되,
> **"기능이 많은 것"이 아니라 "예외 상황에서도 데이터가 안 깨지는 것"** 을 목표로 만든다.

핵심은 가계부 자체가 아닙니다. 가계부는 소재일 뿐이고, 진짜 배우는 건 네 가지입니다:

| 배우는 것 | 왜 배우나 |
|---|---|
| 계층 분리 (모델/저장소/서비스/CLI) | 코드가 커져도 고칠 곳을 바로 찾을 수 있게 |
| 제너레이터 스트리밍 | 데이터가 100만 건이어도 메모리가 터지지 않게 |
| 데코레이터 | 로그·예외 처리 같은 "반복되는 잡일"을 한 곳에 모으게 |
| 타입 힌트 | 함수끼리 주고받는 데이터의 "계약서"를 명확하게 |

## 2. 완성되면 이런 모습

터미널에서 이렇게 씁니다 (명세의 참고 예시 기준):

```
$ python -m budget_app add
날짜(YYYY-MM-DD): 2024-01-15
타입(income/expense): expense
카테고리: food
금액(양수): 15000
메모(선택): 점심
[저장 완료] id=TX-000012

$ python -m budget_app list --limit 3
TX-000012 | 2024-01-15 | expense | food | 15000 | 점심
TX-000011 | 2024-01-14 | income  | salary | 3000000 |
TX-000010 | 2024-01-12 | expense | transport | 20000 |

$ python -m budget_app summary --month 2024-01 --top 3
총 수입: 3000000원
총 지출: 215000원
잔액: 2785000원
예산: 500000원 (사용률 43.0%)
```

명령은 총 9개: `add`(추가), `list`(목록), `search`(검색), `summary`(월별 요약),
`budget`(예산), `category`(카테고리 관리), `update`(수정), `delete`(삭제),
`import`/`export`(CSV 가져오기/내보내기).

데이터는 프로그램을 꺼도 남아 있어야 하므로 `./data` 폴더의 파일(3개 이상)에 저장합니다.
예: 거래 내역 파일, 카테고리 파일, 예산 파일.

## 3. 꼭 지켜야 하는 규칙 (명세 제약)

- **Python 3.10 이상**, **표준 라이브러리만** 사용 (pip install 금지)
- 옵션은 전부 `--옵션명` 형태로 통일, 모든 명령에 `--help` 제공
- 입력의 기본은 **대화형**(프로그램이 물어보면 답하는 방식).
  단 `search/list/summary/export/import/delete`는 옵션 인자 방식 허용
- 오류가 나면 **스택트레이스를 보여주지 말 것** — 대신 "원인 + 해결 힌트"를 출력
  (예: `[오류] 날짜 형식이 올바르지 않습니다` + `[힌트] 예: 2024-01-15`)
- 정상 종료는 exit code 0, 오류 종료는 0이 아닌 값
- 파일을 통째로 읽는 코드 금지 — 읽기는 전부 제너레이터 스트리밍으로
- 최소 3개 모듈, 최소 2개 클래스, 타입 힌트 적용

## 4. 핵심 개념 풀이

과제에 등장하는 용어들을 짧게 풀면:

**JSONL vs CSV** — 둘 다 "한 줄 = 데이터 한 건"인 텍스트 파일 포맷.
JSONL은 한 줄이 `{"id": "TX-1", "amount": 15000, ...}` 같은 JSON이고,
CSV는 `TX-1,15000,...`처럼 쉼표로 구분. 우리는 둘 중 하나를 골라야 함(결정 0-1).

**제너레이터 스트리밍** — 파일 100만 줄을 `readlines()`로 한 번에 메모리에 올리는 대신,
`yield`로 **한 줄씩 꺼내 쓰는** 방식. 다음 줄은 실제로 필요해질 때만 읽힌다.
물을 양동이로 퍼오는 게 아니라 수도꼭지를 트는 것에 비유할 수 있음.

**데코레이터** — 함수를 감싸서 "본업 전후에 하는 공통 잡일"(로그 찍기, 예외 잡기,
시간 재기)을 덧붙이는 문법. `@로그찍기`를 함수 위에 붙이면 그 함수를 호출할 때마다
로그가 자동으로 남는 식. 잡일 코드를 매 함수마다 복붙하지 않게 해준다.

**타입 힌트** — `def add(amount: int) -> Transaction:`처럼 "이 함수는 정수를 받아
Transaction을 돌려준다"를 코드에 명시하는 것. 실행에는 영향이 없지만, 함수끼리
주고받는 데이터의 **계약서** 역할을 해서 잘못 쓰면 도구가 미리 경고해준다.

**dataclass** — "데이터 묶음"용 클래스를 짧게 정의하는 Python 문법.
거래 1건(id, 날짜, 금액, ...)처럼 필드가 여럿인 데이터를 담는 그릇.

**계층 분리 (모델/저장소/서비스/CLI)** — 코드를 역할별로 나누는 설계:
- **모델**: 데이터가 어떻게 생겼나 (Transaction = id + 날짜 + 금액 + ...)
- **저장소**: 파일에 읽고 쓰는 일만 담당
- **서비스**: "월별 요약을 계산한다" 같은 실제 업무 규칙
- **CLI**: 사용자와 대화하는 창구 (입력받기, 출력하기)

이렇게 나누면 "출력 형식을 바꾸고 싶다 → CLI만 고친다",
"저장 포맷을 바꾸고 싶다 → 저장소만 고친다"가 가능해진다.

**원자적 교체 (atomic rename)** — 수정/삭제 때 원본 파일을 직접 고치다가 프로그램이
중간에 죽으면 파일이 반쯤 깨진 상태로 남는다. 대신 **임시 파일에 다 쓴 뒤 이름만
바꿔치기**하면, 어느 순간에 죽어도 "온전한 옛 파일" 아니면 "온전한 새 파일"만 존재한다.
이 과제의 모토("예외 상황에서도 데이터가 안전")를 가장 직접적으로 구현하는 기법.

## 5. 우리는 이렇게 진행한다 (하네스 방식)

이 과제는 Claude가 대신 짜주는 방식이 아니라, 역할을 나눠 진행합니다:

- **학습자(당신)**: 설계 결정을 내리고, 왜 그렇게 했는지 말하고, 나중에 설명 테스트를 통과
- **Claude**: 결정이 필요한 지점을 찾아 선택지와 트레이드오프를 제시하고,
  당신의 결정대로 구현하고, 그 결정이 코드 어디에 반영됐는지 해설

기능 하나마다 6단계를 돕니다:

```
① 명세 확인 → ② 결정 포인트 제시 → ③ 당신이 선택 + 이유 기록
→ ④ 결정대로 구현 → ⑤ 코드 워크스루 → ⑥ 설명 테스트 (통과해야 완료)
```

철칙 두 가지:
- **당신의 결정 기록 없이는 구현을 시작하지 않는다** (③ 없이 ④ 없음)
- **설명 테스트를 통과해야 체크된다** — 코드를 소리내어 읽는 건 통과가 아니고,
  자기 언어로 흐름을 설명해야 통과

## 6. 로드맵 — 무엇을 어떤 순서로 만드나

harness.md의 10개 섹션을 쉬운 말로 풀면:

| # | 섹션 | 하는 일 | 대기 중인 결정 |
|---|---|---|---|
| 0 | 아키텍처 기반 | 저장 포맷, 파일 구성, 모듈 구조, id 방식 등 "집의 뼈대" | 5개 |
| 1 | 공통 인프라 | 데코레이터, 오류 처리, 스트리밍 리더 등 "공용 설비" | 3개 |
| 2 | add | 거래를 대화형으로 입력받아 저장 | 2개 |
| 3 | list | 최신순 목록 출력 (+ 스트리밍과 정렬의 긴장 해결) | 3개 |
| 4 | search | 기간/카테고리/타입/키워드/태그 조건 검색 | 3개 |
| 5 | summary | 월별 총수입/총지출/잔액 + 지출 TOP N | 2개 |
| 6 | budget | 월 예산 저장, summary에 사용률/경고 표시 | 2개 |
| 7 | category | 카테고리 추가/목록/삭제 (사용 중 삭제 처리) | 2개 |
| 8 | update/delete | 수정/삭제 + 파일이 깨지지 않게 하는 안전장치 | 2개 |
| 9 | import/export | CSV로 일괄 등록/내보내기 | 3개 |

0번과 1번이 기초 공사라 먼저 하는 게 자연스럽고, 2번(add)부터는
"저장 → 조회 → 가공 → 수정" 순으로 데이터의 생애주기를 따라갑니다.

## 7. 앞으로 내릴 결정들 — 왜 그게 결정거리인가

전부 24개지만, 성격이 큰 것 몇 개만 미리 감을 잡아두면:

- **저장 포맷 (0-1)**: JSONL은 필드 추가·태그 같은 중첩 데이터에 유연하고,
  CSV는 엑셀로 바로 열린다. 어느 쪽이든 과제는 성립 — 당신의 우선순위가 결정.
- **id 방식 (0-4)**: `TX-000012` 같은 순차 번호는 사람이 읽기 좋지만 "마지막 번호"를
  추적해야 하고, UUID는 추적이 필요 없지만 길고 못생겼다.
- **최신순 + 스트리밍 (3-1)**: "정렬"은 원래 데이터 전체를 봐야 가능한데,
  "전체를 메모리에 올리지 말라"는 제약과 충돌한다. 이 긴장을 어떻게 풀지가
  이 과제에서 가장 생각할 거리가 많은 결정.
- **update 방식 고정 (8-1)**: 옵션 방식(`update --id TX-1 --amount 2000`)과
  대화형 중 하나를 골라 문서에 못박아야 한다. 명세가 "둘 다"를 금지.
- **파일 안전성 (8-2)**: 수정/삭제 중 프로그램이 죽어도 데이터가 안 깨지게 하는 방법.
  명세가 원자적 교체를 권장하고, 보너스 과제 4와도 겹친다.

나머지 결정들은 각 기능에 들어갈 때 선택지·트레이드오프와 함께 제시됩니다.

## 8. 완주 조건

기능이 다 돌아가는 것만으로는 끝이 아닙니다. 명세의 "과제 목표"는
**스스로 설명할 수 있는가**로 정의돼 있습니다:

1. 파일 기반 저장으로 CRUD/검색/요약/입출력을 구현했다
2. 각 계층(모델/저장소/서비스/CLI)의 책임을 설명할 수 있다
3. 제너레이터 스트리밍의 이유와 동작 방식을 설명할 수 있다
4. 데코레이터로 공통 관심사를 분리한 구조와 이유를 설명할 수 있다
5. 타입 힌트의 이점을 실제 코드 예로 설명할 수 있다

그래서 하네스의 설명 테스트가 각 기능마다 붙어 있는 것이고,
마지막에 이 5개를 최종 점검으로 다시 확인합니다.

추가로 `README.md`(실행 방법, 저장 파일 위치/형식, 명령 예시, CSV 스키마)가
필수 산출물입니다 — 이건 잡무로 분류돼 있어서 Claude가 작성하고 당신이 검수합니다.
