거래 파일이 200,000줄일 때 최근 3건만 보고 싶다. 파일을 통째로 메모리에 올리는 방식과, 제너레이터로 필요한 만큼만 당겨 읽는 방식은 무엇이 다른가 — 직접 실행해보면서 비교합니다.

02읽기는 "당겨야" 일어난다 — next() 한 번씩 눌러보기

제너레이터 체인은 뒤에서 앞으로 당기는(pull) 구조입니다. search --type expense에서 지출 2건만 뽑는 상황 — next()를 누를 때마다 요청이 왼쪽으로 전파되고, 데이터가 오른쪽으로 한 건 흘러갑니다. income이 걸리면 filter가 버리고 스스로 다시 당기는 것도 지켜보세요.

03과제 코드에선 이렇게 생겼다

budget_app 저장소 계층에 들어갈 읽기 함수의 뼈대입니다.

def read_lines(path: Path) -> Iterator[str]:
    with open(path, encoding='utf-8') as f:
        for line in f:          # 파일 객체 자체가 이미 한 줄씩 읽는다
            yield line           # ← 여기서 '일시정지'. 다음 next() 때 이 지점부터 재개

# 쓰는 쪽: 소비자가 당기는 만큼만 읽힌다
for tx in take(parse_all(read_lines(data_path)), limit):
    print(format_row(tx))        # limit개 채우면 루프 종료 → 읽기도 멈춤
yield의 본질: 함수가 값을 하나 내놓고 그 자리에 멈춰 서는 것. return은 함수를 끝내지만, yield는 "다음 요청이 오면 여기서부터 계속"이라는 책갈피를 꽂아둔다. 그래서 200,000줄짜리 파일도 메모리에는 늘 "지금 보는 한 줄"만 존재한다.

04이게 과제의 어디에 쓰이나

  • list --limit N — 데모 01 그대로. N건 채우면 읽기 중단.
  • search --type --category … — 데모 02 그대로. 필터를 제너레이터 체인으로 쌓는다.
  • summary --month — 한 줄씩 읽으며 합계 dict에 누적. 전체를 올리지 않아도 집계 가능.
  • 공통 수용 기준: "저장 파일을 읽는 모든 경로가 제너레이터 기반" — readlines() 같은 통째 읽기가 하나라도 있으면 위반.
※ 단순화 노트 — 데모 01은 "읽기 방식"만 비교합니다. 실제 과제의 list는 최신순 정렬이 필요해서 "정렬은 전체를 봐야 한다 vs 스트리밍" 사이의 긴장을 풀어야 하는데, 그게 harness.md의 결정 3-1입니다. 이 페이지는 그 결정의 재료가 되는 기초 개념만 다룹니다.
