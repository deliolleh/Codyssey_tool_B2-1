### 설명 테스트 결과 (통과)

### 설계 결정
- **결정 0-1. 저장 포맷**: JSONL vs CSV (명세: 둘 중 1개 선택)
  - 선택: **JSONL** / 이유: 각 레코드가 key-value로 필드명을 스스로 지니는 자기 서술적 구조라서.
    경험한 DB들의 레코드 구조와 닮아 직관적이고, 위치 기반인 CSV와 달리 줄 하나만 봐도 의미가 읽힌다. (기록일: 2026-10-02)
- **결정 0-2. 파일 분리 구성**: 어떤 데이터를 몇 개 파일로 나눌 것인가 (최소 3개 필수)
  - 명세 예시(참고): `transactions.<fmt>`, `categories.<fmt>`, `budgets.<fmt>`
  - 선택: **엔티티별 기본 3분할 유지** (transactions / categories / budgets, 각 .jsonl)
  - 이유(학습자): 이 시스템은 쓰기보다 읽기가 많은 워크로드라 판단했고,
    읽기에 취약한 사건 저장 방식(축 4)은 그 근거로 기각
  - 참고(Claude 분석을 검토 후 수용): 개인 가계부 규모에선 월별 샤딩(B)의 이점이 체감 불가,
    추가 세분화는 현재 실익 없음(YAGNI). meta·반복내역 등 운영 파일은 해당 결정/기능 시점에 추가 허용
  - (기록일: 2026-10-02)
- **결정 0-3. 모듈 구조**: 권장 구도(CLI/서비스/저장소/모델)를 따를지, 변형할지 — 각 모듈의 책임 경계
  - 명세 클래스 예시(참고): `Transaction`, `TransactionRepository`, `BudgetStore`, `CategoryStore`, `BudgetService` 등
  - 선택: **4계층 + 말단 모듈 2개** — `budget_app/` 패키지에
    `__main__.py / cli.py / services.py / storage.py / models.py / errors.py / decorators.py`
  - 이유(학습자): 책임은 최대한 구분하는 쪽을 선호. A(권장 4계층)를 베이스라인으로 두고
    "무엇을 더할가"를 검토해 부속 2개만 추가
  - 참고(Claude 분석을 검토 후 수용): 네 계층의 책임은 첫 기능부터 전부 존재(YAGNI 통과),
    errors/decorators는 전 계층 공용 말단 모듈 — 특정 계층 소속 시 순환 import 위험, 섹션 1에서 즉시 필요.
    `commands/` 분리는 아직 고통이 없으므로 보류(기각 아님)
  - 경계 규칙: cli만 input/print를 안다 · storage만 파일 경로를 안다 · services는 둘 다 모른다(모델만 다룸)
  - (기록일: 2026-10-02)
- **결정 0-4. id 생성 방식**: UUID vs 순차 번호 vs 타임스탬프 기반 (유일성 보장 방법 포함)
  - 참고 예시: `TX-000012` 형태(순차 번호 + 접두사) — 비구속
  - 선택: **순차 번호(TX-000012 형식) + 전용 meta 파일 카운터(A-2)** — 저장 파일은 4개가 됨
    (transactions / categories / budgets / meta)
  - 이유(학습자): 사용자가 직접 타이핑하는 id라 순차 번호가 무난하다고 판단.
    카운터를 모델(클래스)에 두는 방안을 검토했으나 프로세스 종료 시 증발함을 확인,
    상태는 디스크에 있어야 하므로 전용 카운터 파일에 도달(A-2 재발명)
  - 부속 규칙(Claude 제안 수용): id 포맷 규칙은 models, 카운터 영속화는 storage 소속(0-3 경계 규칙).
    쓰기 순서는 **카운터 먼저 갱신, 거래 나중 저장** — 사고 시 중복 id 대신 무해한 번호 구멍.
    번호 재사용 없음(단조 증가)
  - (기록일: 2026-10-07)
- **결정 0-5. 카테고리 초기 상태**: 기본 카테고리 자동 생성 vs `category add` 선행 안내 후 add 차단 (명세: 둘 중 택1 명확히)
  - 선택: **안 A + 투명한 안내** — 기본 카테고리 자동 생성하되, 생성 시 목록과
    수정 방법(category add/remove)을 명시적으로 출력. 대화형 마법사(ii)는 기각
  - 이유(학습자): 첫 사용 마찰이 없는 A를 베이스로 하되, 사용자에게 기본 목록을 보여주고
    수정 경로를 열어줌 — A의 약점("몰래 만든 데이터")을 투명한 안내로 상쇄
  - 부속(확정, 2026-10-07): 기본 카테고리 13개 — 토스 '내 소비' 대분류를 참고해 한 단어로 축약
    (지출) 식비, 카페, 유흥, 쇼핑, 교통, 주거, 통신, 의료, 여가, 생활 / (수입) 급여, 용돈 / (공용) 기타
  - 세분화 규약(학습자): 계층 구조 없음(1단 평면). 더 세밀한 분류가 필요해지면 소분류를
    같은 평면의 새 카테고리로 `category add` (예: 배달, 외식). 묶어 보기가 필요하면 tags 활용.
    계층이 없으므로 자동 합산(rollup)은 없음을 인지하고 선택

## 1. 공통 인프라 (데코레이터 · 예외/종료 코드 · 스트리밍 리더)

상태: `[x]` (2026-10-11 설명 테스트 2문항 통과)

### 수용 기준
- [x] 데코레이터 1개 이상이 구현되어 실제 함수에 적용되어 있다 — 3종:
  @logged/@timed(services.initialize), @translates_oserrors(storage I/O 4곳, 제너레이터 대응형)
- [x] 저장 파일을 줄 단위로 읽어 `yield`하는 제너레이터가 존재하고, 모든 조회 기능이 이를 통해 읽는다 — iter_records
- [x] 의도적으로 오류를 발생시키면 스택트레이스 없이 원인+힌트가 출력되고 exit code가 0이 아니다
  — 실측 5경로: 정상 로그(INFO 시작/완료/ms), 깨진 JSON(exit 1 + ERROR 기록),
  지연된 OSError 번역(첫 next()에서 StorageError, __cause__ 보존), 예상 밖 예외(화면 2줄 + 전문은 app.log),
  취소 모사(exit 130)

### 설명 테스트 결과 (통과)
- 데코레이터 — import=파일을 위에서 아래로 실행, @줄도 실행문이라 그 순간 timed(logged(f)) 조립(교환원 고용).
  호출=양파 즉시 실행(보통 함수는 생성 단계 없음 — 제너레이터와 대비). 분리의 실체=잡무 코드가 본업
  몸체에서 사라져 decorators.py에 1벌, 적용은 @ 한 줄. 부수 학습: @의 치환 실체, functools.wraps=명찰,
  클로저=배낭, *args/**kwargs=만능 중계, %-포맷의 지연 평가
- 제너레이터(실전) — 메모리 최대 1줄, 읽기 방아쇠=소비자의 반복(숨은 next(): for ①은 제너레이터를,
  for ②는 파일 객체를 당김 — 당김의 릴레이), any()의 단락 평가로 100만 줄에서도 1줄만 읽고 종료

### 설계 결정
- **결정 1-1. 데코레이터 범위**: 무엇을(예외 처리/로그/시간 측정) 몇 개 만들고, 어느 함수들에 적용할 것인가
  - 선택: **C안 — 3종 세트.** `@logged`(실행 일지) + `@timed`(시간 측정)는 services에,
    `@translates_oserrors`(OS 예외 → StorageError 번역)는 storage에.
    로그 목적지는 **data/app.log 단일 파일**, 각 줄에 레벨 필드(INFO/ERROR)
  - 이유(학습자): 명세 방향성과의 정합을 기준으로 요청·검토 후 채택 —
    ① 명세가 데코레이터 예시로 항상 셋(예외/로그/시간)을 호명, ② 스택트레이스 금지 위반 구멍
    (OS 예외)은 어차피 막아야 하는 숙제라 데코레이터로 막으면 요구 두 개를 한 번에 충족,
    ③ 명세 예시 화면에 로그가 없음 → 화면이 아닌 파일로. 로그 파일 분리는 과하다고 판단
    (볼륨 없음 + 시간순 통독이 주 패턴), 종류 구분은 레벨 필드로
  - 완화책(수용): 번역 데코레이터는 좁은 타입(OSError)만 잡는다 · `raise ... from exc`로
    원인 사슬 보존 · 적용은 storage 한 계층 한정. 데코레이터는 기록만 하고 삼키지 않는다(re-raise)
  - (기록일: 2026-10-10)
- **결정 1-2. 예외 전략**: 커스텀 예외 계층을 둘 것인가, 어디서 잡아 메시지로 변환할 것인가 (잡는 위치의 단일화 여부)
  - 선택: **B안 — 단일 관문(cli.main) + 안전망.** BudgetError 가족 → 원인+힌트 출력,
    예상 밖 예외(버그) → "예상치 못한 문제" 안내 + 스택트레이스 전문은 app.log에 ERROR 기록.
    양쪽 모두 exit 1. 예외 계층은 errors.py(기존) 유지
  - 이유(학습자): 명세의 "오류는 원인+해결 힌트로 출력"은 일부 오류가 아니라 **모든 오류에
    동일하게** 적용하라는 의미로 해석 — 버그發 예외라도 스택트레이스가 화면에 나가면 위반
  - 수용(완화책): 버그가 조용해지는 위험은 exit 1 유지 + 로그에 전문 보존으로 상쇄.
    핸들러별 개별 except(C안)는 변환 코드 9벌 복붙이라 기각
  - (기록일: 2026-10-10)
- **결정 1-3. 대화형 입력 중단(Ctrl+C / EOF) 처리**: 명세 밖 지점 — 어떻게 종료할 것인가
  - 선택: **A안 — 조용한 취소.** Ctrl+C/Ctrl+D 공통: "[안내] 입력을 취소했습니다.
    저장된 것은 없습니다." 출력 후 **exit 130**. 처리 위치는 1-2의 단일 관문. 취소 확인 질문(B) 기각
  - 이유(학습자): 종료 코드 0/1은 취소가 정상인지 비정상인지 사용자 의도를 단정해야 하는데
    단정할 수 없음 — 130은 해석 없이 "중단됨"이라는 사실만 전달 (128+SIGINT(2) 관례)
  - 수용: EOF는 엄밀히 시그널이 아니나 사용자 관점에선 같은 "입력 중단"이라 경로 통일.
    B 기각은 지키는 가치(입력 10초) 대비 비용(영구 UX 마찰·확인 중 재중단/EOF/파이프 지뢰·재개 로직) 검토 후
  - (기록일: 2026-10-10)

### 설명 테스트
- 데코레이터가 호출을 감싸는 과정(정의 → 적용 → 호출 시점)을 코드 낭독 없이 흐름으로 설명할 수 있는가? 왜 공통 관심사를 데코레이터로 분리했는가?
